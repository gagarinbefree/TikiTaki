# Zero-Dependency 2D Swipe Engine — задание для Codex

Разработай production-ready библиотеку TikiTaki на TypeScript для свайп-навигации по двумерной сетке с переменной длиной строк (Ragged Grid). Свайпы вверх, вниз, влево, вправо переключают полноэкранные элементы с плавной анимацией как в TikTok, но без видеоплеера, backend и рекомендательной системы. Начни с архитектуры и первого этапа TDD; не реализуй всё одним изменением.

## 1. Требования

- TypeScript: `strict: true`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`.
- **Ноль runtime-зависимостей** основного пакета. Без импортов Vue, React, jQuery или UI-фреймворков в ядре.
- Цель — актуальный Google Chrome Desktop и Android; остальные браузеры можно не поддерживать.
- Pointer Events для мыши, касаний и пера; `requestAnimationFrame`, CSS `translate3d` для движения.
- Независимое ядро, пригодное для Vue 3 и React. SOLID, KISS, DRY.
- Строгий TDD: RED → GREEN → REFACTOR для каждого этапа.
- Unit, integration, Chrome E2E; TypeScript typecheck, ESLint, Prettier и production build.

## 2. Модель сетки

Каждая строка имеет произвольную положительную длину. Координаты `(row, col)` индексируются с нуля. Содержимое ячеек произвольное: HTML, видео, изображения, компоненты.

```typescript
const grid = [
  ['A1', 'A2', 'A3', 'A4', 'A5', 'A6', 'A7', 'A8', 'A9', 'A10'],
  ['B1'],
  ['C1', 'C2', 'C3'],
  ['D1', 'D2', 'D3', 'D4', 'D5'],
];
```

## 3. Строгая навигация

- Свайп **вверх**: следующая строка (`row + 1`), **всегда `col = 0`**.
- Свайп **вниз**: предыдущая строка (`row - 1`), **всегда `col = 0`**.
- Свайп **влево**: следующая ячейка текущей строки (`col + 1`).
- Свайп **вправо**: предыдущая ячейка текущей строки (`col - 1`).
- Если переход невозможен, позиция **полностью сохраняется**, включая столбец; на вертикальной границе не сбрасывать `col`.
- В строке длиной 1 горизонтальная навигация недоступна.
- Один жест — максимум одна соседняя ячейка. Никаких диагональных переходов по двум осям.
- Не запоминать позиции предыдущих строк. После любого успешного вертикального перехода открывается первая ячейка.

Пример: `A10 → (вверх) B1 → (вверх) C1 → (влево) C2 → (вниз) B1 → (вниз) A1`.

## 4. Gesture Engine

Выделить состояния `idle | tracking | dragging | settling`.

1. На `pointerdown` запомнить координаты, время и pointer ID.
2. На `pointermove` после dead zone определить преобладающую ось и зафиксировать её до окончания жеста.
3. Текущий экран следует за указателем; соседний появляется с соответствующей стороны.
4. На `pointerup` определить переход по расстоянию **или** скорости жеста.
5. Если порог не достигнут — плавно вернуть экран; иначе завершить переход.
6. На границе использовать упругое сопротивление, но не переключать экран.
7. На время settling блокировать конфликтующие жесты.
8. Обрабатывать `pointercancel`, `lostpointercapture`, повторные касания, резкую смену направления, диагональные жесты.
9. На `destroy()` удалять обработчики, отменять RAF/анимации, освобождать ресурсы.

Конфигурируемые параметры:

```typescript
interface GestureOptions {
  distanceThreshold: number;
  velocityThreshold: number;
  axisLockThreshold: number;
  animationDuration: number;
  edgeResistance: number;
}
```

Задокументировать единицы измерения, диапазоны, значения по умолчанию и валидацию. Учитывать смену направления внутри одного жеста.

## 5. Анимация и DOM Renderer

- Отделить **Navigation Engine**, **Gesture Engine** и **DOM Renderer**.
- CSS `transform: translate3d(...)`; обновления движения через `requestAnimationFrame`.
- Плавное следование за пальцем, завершение, возврат, сопротивление на краях без рывков.
- Не менять глобальные стили; `touch-action: none` только на управляемом контейнере.
- Не допускать layout thrashing и конфликтующих анимаций.
- Рендерить только текущую ячейку и необходимые соседние (для MVP — до четырёх); не создавать всю большую сетку.
- Не создавать несуществующих соседей. Учитывать, что вертикальный сосед **всегда** имеет `col = 0`.
- При изменении размеров контейнера пересчитывать геометрию без рассинхронизации.
- Не привязывать визуальный движок к содержимому ячейки.

## 6. Публичный API

Предлагаемый контракт (допускаются обоснованные улучшения):

```typescript
interface Position {
  readonly row: number;
  readonly col: number;
}

type Direction = 'up' | 'down' | 'left' | 'right';

interface SwipeEngineOptions<T> {
  container: HTMLElement;
  grid: readonly (readonly T[])[];
  initialPosition?: Position;
  gesture?: Partial<GestureOptions>;
  renderCell: (item: T, position: Position) => HTMLElement;
  onPositionChange?: (position: Position, previous: Position) => void;
}

interface SwipeEngine<T> {
  getPosition(): Position;
  navigate(direction: Direction): Promise<boolean>;
  goTo(position: Position): Promise<boolean>;
  updateGrid(grid: readonly (readonly T[])[]): void;
  destroy(): void;
}
```

Валидация входа, readonly-данные, несколько независимых экземпляров, без singleton. `destroy()` идемпотентен. Определить семантику `Promise<boolean>`, программной навигации и вызовов во время анимации; не оставлять незавершённых Promise. При обновлении сетки гарантировать допустимую текущую позицию и согласованность DOM.

## 7. Vue 3 и React: демонстрации и адаптеры

Создать отдельные рабочие примеры для Vue 3 (Composition API, mount/unmount) и React (функциональные компоненты, `useRef`, `useEffect`, cleanup, StrictMode). Показать создание движка, передачу контейнера, рендеринг, обновление сетки и уничтожение.

**Особо важный технический момент для Codex:** полноценные Vue/React-компоненты нельзя просто преобразовать в `HTMLElement`: у них собственные деревья, реактивность и жизненный цикл. Предусмотри расширяемый контракт адаптера рендеринга поверх независимого ядра, поддерживающий mount/update/unmount и освобождение ресурсов. Ядро не должно импортировать Vue/React и вмешиваться в DOM, управляемый фреймворком. Для React рассмотри родительский root и portals/refs вместо создания отдельного root на каждую ячейку, если это надёжнее. Обеспечь корректность StrictMode, отсутствие двойных подписок и утечек. Framework-specific адаптеры должны быть изолированы и не входить в runtime-зависимости основного пакета; при необходимости оформляй их отдельными необязательными entry points/пакетами с peer dependencies. Тестируй mount/update/unmount, переходы, обновление сетки и destroy.

## 8. TDD и тесты

Перед кодом каждого модуля написать падающие тесты (**RED**), затем минимальную реализацию (**GREEN**), затем рефакторинг (**REFACTOR**). Не пропускать фазы и не выдавать непроверенные тесты за прошедшие.

Unit/integration тесты должны покрывать:

- Все направления и границы, включая сохранение `col` при неуспешном вертикальном свайпе.
- Переход в `col = 0` из любого столбца при успешном вертикальном свайпе.
- Строки разной длины и строки с одной ячейкой.
- Быстрый короткий и медленный длинный свайп, недостаточный жест.
- Смену направления, диагонали, axis lock, edge resistance.
- Повторные жесты и блокировку при settling.
- `pointercancel`, потерю capture, destroy, обновление сетки.
- Несколько экземпляров, повторную инициализацию, отсутствие утечек.
- Жизненный цикл Vue/React адаптеров.

## 9. Chrome E2E

Использовать Playwright с **Google Chrome** (не подменять тестирование реального браузера только jsdom). Проверить мышь и touch emulation; дополнительно документировать необходимость ручной проверки на физическом Android-устройстве.

Покрыть переходы из `A10` в `B1`, обратно в `A1`, горизонтальные ограничения строки `B1`, быстрые последовательные жесты, отмену, реальные DOM-анимации, отсутствие скачков и console errors, Vue/React demos. Проверять конечную позицию и визуальное состояние, а не только вызов функции.

- Chrome Desktop/Android как целевые платформы; выполнены доступные Chrome E2E, физический Android отдельно отмечен, если не проверен.
- Zero-runtime-dependency ядро; TypeScript strict, ESLint, unit/integration, Chrome E2E и production build проходят.
- Рабочие Vue и React demos, корректный lifecycle, отсутствие известных утечек.
- Публичный API и архитектура задокументированы.
